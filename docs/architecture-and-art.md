# Архитектура, интерфейс и графика

Это проектное решение для обозначенного MVP, не уже реализованная архитектура.

## Выбранный стек

**React + TypeScript + Vite; PixiJS для сцены; Zustand для состояния; IndexedDB для сохранения.** Упаковка как PWA после проверки офлайн-запуска. Backend в MVP не нужен.

React управляет обычными экранами, кнопками, меню и доступностью. PixiJS отображает питомца, слои комнаты, анимации и касания объектов. TypeScript описывает правила и данные. Vite собирает приложение. Zustand хранит согласованное состояние; сам по себе он не заменяет проверку правил и сохранение.

PixiJS — 2D-рендерер: [официальное введение](https://pixijs.com/8.x/guides/getting-started/intro), [публичный репозиторий, проверенный через GitHub](https://github.com/pixijs/pixijs). Для хранения структурированных данных используем транзакционную IndexedDB: [документация MDN](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API). Сборщик: [Vite](https://vite.dev/guide/).

### Почему этот выбор

| Вариант | Оценка для нашей игры |
|---|---|
| Только React + CSS/SVG | Подходит для раннего макета, но слоёные спрайты, кадры анимации и сценические эффекты удобнее централизовать в рендерере |
| **React + PixiJS** | Выбран: обычный интерфейс плюс одна 2D-сцена, без физики и десятков игровых миров |
| React + Phaser | [Phaser — полноценный игровой фреймворк](https://docs.phaser.io/phaser/getting-started/what-is-phaser). Имеет смысл при нескольких мини-играх и сложных игровых сценах; сейчас часть возможностей избыточна |
| Three.js / React Three Fiber | Нужны для настоящей 3D-сцены; добавляют работу со светом, камерой, материалами, одеждой и производительностью. Для первой проверки эмоционального цикла не обязательны |
| Supabase / Firebase | Не решают проблему интересности игры. Аккаунты, синхронизация и серверная экономика появятся только с подтверждённой потребностью |

До начала реализации фиксировать совместимые актуальные стабильные версии и lockfile. Не обещать конкретные версии библиотек на основе этого документа: проверка совместимости входит в bootstrapping. Зависимостей мало, но не экономим на валидации данных и тестах состояния.

## Состояние и команды

Один источник истины: сериализуемый GameState с версией схемы, revision, питомцем, потребностями, временем пересчёта, монетами, XP, инвентарём, выбранными вещами, заданиями, выданными наградами, привычками, воспоминаниями и настройками.

Интерфейс отправляет команды `feed`, `pet`, `wash`, `startSleep`, `wake`, `buyItem`, `equip`, `applyRoom`, `claimReward`. Обработчик сначала пересчитывает прошедшее время, затем валидирует команду, вычисляет новое состояние и сохраняет его. Рендерер подписывается на нужные изменения и запускает визуальную реакцию.

Правила — чистые функции: одинаковое состояние, время и команда дают одинаковый результат. Дневной набор заданий определяется сохранённым seed/днём и остаётся одинаковым после перезагрузки. Не генерировать новый набор на каждом открытии.

Ни React-компонент, ни callback завершения анимации не начисляют награду напрямую. Иначе пропуск кадра или повторная подписка могут выдать её дважды.

## Время и rendering loop

Видимая анимация использует собственный ticker. Потребности не меняются по числу кадров. Игровые часы считаются по timestamp; активный UI обновляет отображение с невысокой частотой и при действии.

При скрытии вкладки анимации и звук останавливаются. При возврате выполняется один пересчёт по timestamp с правилами ограничения отсутствия. Не запускаем тысячи пропущенных тиков. В активной сессии длительности измерять монотонными часами, при восстановлении — системным временем с обработкой отрицательного и слишком большого интервала.

Размер сцены логический; позиция объектов не зависит от пикселей конкретного экрана. Экранные координаты касания переводятся в координаты сцены. Декор и питомец используют постоянные точки привязки; для перекрытий задан порядок слоёв.

## Сохранение — первая инфраструктурная задача

IndexedDB хранит текущий валидный снимок, предыдущий валидный снимок и информацию о версии. Экономическая команда сохраняет новый снимок атомарно. Очередь команд предотвращает конфликт быстрых нажатий.

Проверка загрузки: конечные числа, допустимые диапазоны, неотрицательные целые количества/монеты, существующие ID контента, доступность надетых вещей, структура наград, корректная версия. Неизвестный визуальный ресурс может получить placeholder; невалидное экономическое состояние не принимается молча.

При повреждении: попробовать предыдущий валидный снимок; сохранить повреждённый для диагностики; предложить импорт. Новый старт с удалением прогресса — только явным действием игрока. Более новая неподдерживаемая версия не перезаписывается старой программой.

Экспорт и импорт — файл JSON с проверкой схемы и ограничением размера. Импорт не исполняет код и не загружает произвольные внешние ресурсы. Перед заменой создаётся резервная копия.

При отказе хранилища можно предложить явно обозначенный временный режим и экспорт, но нельзя показывать «сохранено». Покупки и выдачи наград должны либо откатываться, либо иметь явно показанный несохранённый статус; для MVP выбираем откат транзакции.

Несколько вкладок: одна активная записывающая сессия; вторую переводить в режим просмотра с кнопкой переноса управления. Блокировку делать через механизм владения и revision в транзакции IndexedDB, а не полагаться только на сообщения вкладок. Перед захватом читать актуальное состояние. Тестировать аварийное закрытие владельца.

Хранилище браузера может быть очищено пользователем или системой. Экспорт должен быть заметен в настройках; обещание «навсегда сохранено» для локальной версии неприемлемо. Это одна из причин добавить облако позже, но не до проверки продукта.

## Интерфейс и дизайн-система

Главный экран — комната. Сверху имя/уровень, монеты и настройки; под ними компактные потребности. Снизу четыре подписанные кнопки заботы. Нижняя навигация: «Дом», «Вещи», «Магазин», «Альбом». Задания доступны одной небольшой кнопкой на главной сцене.

Покупки и гардероб открываются нижней панелью, чтобы питомец оставался виден. В каждый момент максимум одна модальная панель. Доступны кнопка закрытия, системное «назад» и корректный возврат фокуса. Не ставить несколько всплывающих наград поверх друг друга.

| Элемент | Рабочее правило |
|---|---|
| Палитра | Фон #F6F0E4, тёмный текст #302F35, шалфей #A9BBA2, глина #D39A82, акцент #6C647D |
| Текст | Системный шрифт с кириллицей; основной 16 px, заголовки 22–28 px; контраст проверяется отдельно |
| Ритм | Шаги отступов 4/8/12/16/24/32 px |
| Кнопки | Минимальная целевая область 48×48 CSS px; подпись, понятное активное/недоступное состояние |
| Карточки | Предмет крупнее метаданных; цена видна до покупки |
| Состояния | Не только цвет: значок + подпись для ошибки, блокировки и успеха |
| Движение | Короткая реакция, мягкие переходы; настройка уменьшения движения |
| Safe areas | Отступы учитывают вырезы телефона и нижнюю системную полосу |
| Звук | Только после взаимодействия пользователя; можно отключить; важные события понятны без звука |

Питомец не должен скрываться под открытым магазином. Все действия сцены имеют доступные HTML-эквиваленты. На клавиатуре можно выполнить основные действия. Целевая ширина — от 360 CSS px; отдельно проверить 320 px без потери функций, landscape и увеличение текста до 200%.

## Как использовать 3D-навыки художника

Для MVP предлагаем **моделировать в Blender/Maya, рендерить в прозрачные 2D-кадры, отображать их в PixiJS**. Получается объёмная авторская графика при фиксированной камере и контролируемой стоимости рендеринга на телефоне.

Это не настоящее вращаемое 3D. Загрузка GLB не станет простой заменой PNG: для realtime 3D понадобятся другой рендерер, анимационные привязки, освещение, коллизии одежды и отдельная проверка производительности. Состояние и правила можно сохранить, слой отображения потребуется доработать.

### Пакет первой графики

- Один персонаж: единая модель/rig, три цветовых варианта, восемь коротких клипов.
- Одна базовая комната с фиксированной камерой, выделенные слои стен/пола/предметов.
- 12 элементов оформления и шесть аксессуаров суммарно со стартовыми.
- Четыре изображения еды, набор небольших UI-иконок.
- Восемь воспоминаний используют сцену и те же ресурсы, без восьми новых полноценных анимационных роликов.
- Несколько мягких звуков действий и одна необязательная фоновая петля; собственные или с документированной лицензией.

### Конвенции

| Ресурс | Начальное соглашение |
|---|---|
| Имена | `pet_neighbor_idle_v001`, `prop_reading_lamp_v001`, `wear_scarf_clay_v001` |
| Исходники | `.blend`/`.ma` вне поставляемого web-пакета; в Git LFS или отдельном художественном хранилище после выбора процесса |
| Питомец | Рабочие кадры 512×512, одинаковая камера и базовая точка ног; итоговое разрешение уточнить на телефоне |
| Предметы | PNG/WebP с альфой; размер зависит от экранного размера; не масштабировать все предметы одинаково |
| Анимация | Обычно 8–12 fps для рисованного впечатления; непрерывное движение сцены интерполируется отдельно |
| Атласы | Начальный предел 2048×2048; измерять декодированную GPU-память, а не только размер WebP |
| Слои | Тень, задние аксессуары, тело, передние аксессуары, эффекты; порядок определён манифестом |
| GLB/GLTF позже | Метры, нормализованные трансформации, документированная ориентация, имена клипов и attachment points |

Одежда в MVP — голова и шея, без полноразмерного костюма. Аксессуары используют точки привязки на каждом кадре либо заранее подготовленные слои. Плоско наложенный шарф без учёта поворота головы недопустим; это отдельный тест art pipeline на раннем этапе.

### Замена графики без редактирования кода

Для замены существующего ресурса художник экспортирует файлы по предоставленному шаблону размеров/имён и подменяет их в папке. Манифест сопоставляет стабильные игровые ID с файлами, anchor points и клипами. Валидатор показывает отсутствующий кадр, неправильный размер, несовместимый слот или дублирующийся ID понятным отчётом.

Новый предмет требует записи в каталоге и проверки привязок; это уже не простая подмена картинки. До MVP разработчик ведёт JSON-каталог, художник работает по шаблону и получает preview. Простой визуальный редактор каталога можно добавить в 0.4, если обновление вручную действительно мешает.

Критерий удобства: художник заменяет один предмет и idle-питомца по README без изменения TypeScript, затем видит их в preview. Если это не удаётся — процесс не считается завершённым.

## Бюджеты производительности — цели для проверки

Начальная загрузка до 8 MB сжатых ресурсов; минимум 30 fps на выбранном среднем Android-телефоне; цель 60 fps на более мощных устройствах; видимая реакция на нажатие до 100 ms в обычном состоянии. Загружать каталоги и дополнительные анимации по необходимости. Все значения — цели, не результат измерений.

Первый этап должен назвать два реальных тестовых устройства: Android и iPhone, версии ОС/браузера и сеть. Без этого нельзя заявлять «mobile-ready». WebKit в автоматических тестах полезен, но не заменяет настоящий Safari на iPhone.

## Дальнейшая платформа

PWA: манифест, cache для приложения и нужных ресурсов, проверка первого запуска онлайн, повторного офлайн-запуска и обновления схемы сохранений. Простое наличие манифеста не означает работоспособный offline.

Для нативных контейнеров рассмотреть [Capacitor](https://capacitorjs.com/docs): он позволяет использовать web-приложение в iOS/Android-проекте. Отдельно остаются жизненный цикл, устройства, сборки, подписи, магазин, резервное копирование и покупки. Упаковка не гарантирует публикацию.

Будущее облако: добавить SaveRepository через серверный API, аккаунт по желанию, версионирование и явное разрешение конфликтов. Не применять слепое «последний timestamp победил» к инвентарю и валюте. Если появляются реальные платежи или обмен между игроками, сервер становится источником истины для покупок и наград. Выбор Supabase/Firebase делать тогда по фактическим требованиям.
